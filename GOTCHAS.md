# Gotchas

## Database Migrations

- **Inventory/incident tables were dropped in v3.0.0; Zammad ticketing in v4.0.0.** Do not add them back. Configuration management (Terraform/Ansible/local config files) is the source of truth for inventory; tickets/incidents live in each client's own systems (Zammad was decommissioned fleet-side); Uptime Kuma is the source of truth for monitoring. ops-brain stays on its lane: handoffs, knowledge, and stateless briefing delivery.
- **`knowledge.source_incident_id` was dropped** in the same migration. Provenance now lives entirely in the `author` column.
- **Fresh disposable databases need pgvector installed before migrations.** The application-owned `ops_brain` role is deliberately not a superuser and cannot install the `vector` extension on this PostgreSQL build. Create the disposable database with `ops_brain` as owner, then have a privileged PostgreSQL role run `CREATE EXTENSION IF NOT EXISTS vector` in that database before the test suite. CI follows the same order; do not grant the application role superuser just to make local tests convenient.
- **Re-applying a still-untracked migration after editing it.** If a new migration file has already run against your local dev DB and you edit the file before committing, sqlx will refuse to boot with `VersionMismatch(<version>)` because the checksum drifted. Recipe to recover: `DELETE FROM _sqlx_migrations WHERE version = <N>;` then `DROP` the indexes/columns it added; re-run. Only safe while the migration is unreleased — never do this once it has merged.

## Commit workflow

- **PreToolUse `cargo fmt --check` hook blocks the whole Bash invocation, including staging.** When you chain `git add <files> && git commit -m "..."` and the fmt hook trips, neither half runs — so untracked files you intended to include are still untracked. After `cargo fmt`, re-stage the originally-intended set explicitly (especially new migrations and other untracked files); `git add -u` alone only catches tracked-file edits. Caught once on 2026-05-12 (v3.1 PR #53), required a follow-up commit; squash-merge cleaned it up but is avoidable.
- **Fleet-private strings are blocked at commit + CI time — the CI half is hash-based and scans the whole tree (rewritten 2026-08-24, CC-HSR ruling `01a03571`).** `.github/workflows/secret-scan.yml` runs `.github/scripts/fleet_string_guard.py`, which walks every tracked file and compares salted SHA-256 digests against `.github/fleet-denylist.sha256`. **There is no `PATTERN` literal any more** — the old workflow enumerated, in the clear on a public repo, the complete set of strings it existed to protect, which made it the single best place to look for exactly those values. Consequences worth knowing:
  - **Run it locally — it needs no arguments and no secret:** `.github/scripts/fleet_string_guard.py`. Do this before pushing; do not reconstruct a pattern by hand.
  - **Matching is case-insensitive and position-independent.** The old regex was case-*sensitive*, so it never saw the 13 lower-case occurrences in the normalize-machine-names migration — only the 3 upper-case ones in its header comment. A guard that matches one case of a hostname matches roughly none of them. The scan slides a byte window over each run of identifier characters, so a value glued to a prefix or suffix (`xx<class>yy`, a URL path segment) is caught too; it also re-scans NUL-stripped bytes so UTF-16 cannot hide one.
  - **The denylist publishes each value's byte length** (`<length>:<digest>`). Deliberate, and strictly less than either predecessor leaked. It is what makes the windowed scan possible.
  - **Fail-closed in four places**, each with a test: missing denylist, malformed entry (anything not `<length>:<64 hex>`), an entry count that does not match `EXPECTED_CLASSES` in the script, and an unknown CLI argument. A file that is unreadable or over the 16 MB cap prints `::warning::NOT SCANNED` and the summary line says so — an unscanned file must never be silently folded into "Clean".
  - **`--no-allowlist`** re-scans waived paths, which is how you get an occurrence count out of an allowlisted file.
  - **Output carries no plaintext at all** — a hit prints `path:line: <guarded class 0ca3dac0>`, naming a digest prefix. Masking (`Z****9`) was the first cut and was rejected in review: it publishes first character, last character, and exact length into a log that is world-readable on a public repo. The old workflow was worse still — it echoed the entire pattern on every failure.
  - **The guard no longer exempts its own files.** The old one excluded `secret-scan.yml` from its own scan, which is how it carried the list it was policing.
  - **Add a new guarded class without writing it down:** `.github/scripts/fleet_string_guard.py --emit-hash < value.txt` (or run it bare and paste, Ctrl-D), append the emitted `<length>:<digest>` line to `.github/fleet-denylist.sha256`, and bump `EXPECTED_CLASSES`. **Do not use a `printf '%s' 'value' | …` pipeline** — that puts the value in `argv`, where `ps`, shell history, and an agent's transcript store all record it.
  - **Waivers are explicit and noisy.** `.github/fleet-denylist-allow.txt` exempts a path; an allowlisted path that still carries a guarded string prints a `::warning::` on every run, so a waiver cannot quietly become permanent.
  - **Fail-closed:** a missing or empty denylist aborts rather than certifying the tree clean.
  - **The deploy-host class was dropped** — publicly resolvable, serves public HTTPS, enumerated in Certificate Transparency. It was never confidential; guarding it generated churn for no confidentiality gain. Three client-private classes remain.
  - **The local and CI guards are converged as of 2026-08-25** (dotfiles `97d1c79`). The dotfiles pre-commit hook no longer has a pattern of its own — it shells out to this same script against this same denylist, so a local pass and a CI pass now mean the same thing. It **fails closed**: a missing `python3` or a missing script blocks the commit rather than allowing it, because "the checker isn't here" must not be indistinguishable from "the check passed". `ALLOW_FLEET_STRINGS=1 git commit ...` still bypasses. Note the behaviour change that follows from converging: the hook now scans the whole tree, so a pre-existing occurrence anywhere blocks *any* commit until it is waived or removed — that is the point, not a regression.
- **`migrations/20260426000002_normalize_handoff_machine_names.sql` cannot be edited to remove the hostnames, and this is a hard constraint, not a preference.** `src/db.rs` runs `sqlx::migrate!("./migrations")` at startup, and sqlx-core 0.8.6 `migrate/migrator.rs:176` returns `MigrateError::VersionMismatch` when an applied migration's checksum no longer matches the file. There is no ignore-checksum option in the `Migrator` API (`set_ignore_missing` covers *missing* migrations, not changed ones). So any content change to that file — including a pure-comment scrub — stops the deployed instance from booting until `_sqlx_migrations` is updated in lockstep on the production database. Remediating it is a coordinated deploy + DB mutation, not a code change. It is allowlisted in the guard for exactly this reason, with the exit condition recorded in the allowlist file.
  - **Squashing the migration set to a baseline does not escape this — it is worse. Verified at source 2026-08-25** (CC-HSR ruling `01a03a26`), because the intuition that a baseline is the clean way out is wrong and load-bearing. In `sqlx-core` 0.8.6 `migrate/migrator.rs`, `run_direct` matches each resolved migration against the applied set and the `None` arm is an unconditional `conn.apply(migration)`. **There is no version-ordering guard in that loop at all** — sqlx never checks that an unapplied migration is newer than the highest applied one. So a baseline whose version is absent from `_sqlx_migrations` *executes against populated production data*, which is strictly worse than the scrub's failure mode (a loud, reversible boot failure). Choosing the version does not rescue it: reuse an already-applied version and you land in the `Some` arm with a drifted checksum, i.e. `VersionMismatch` and a dead instance. `set_ignore_missing` genuinely covers the *missing* half (`validate_applied_migrations`, `migrator.rs:32`, returns `Ok` early) and nothing else — and enabling it needs a `src/db.rs` change, since `sqlx::migrate!` yields a non-`mut` `Migrator`. Net: squash costs the scrub's coordinated deploy and DB write, **plus** a code change, **plus** a hand-written `_sqlx_migrations` row. It only looks clean from a fresh clone. **Decision recorded in `TODO.md`: accept the file; attach any cleanup to a DB rebuild you are already paying for.**

- **~~The local guard silently does not run for `cd <path> && git commit ...`~~ — RETRACTED, re-measured 2026-08-25. It does run.** The 2026-08-20 entry claimed the `PreToolUse` `"if": "Bash(git commit*)"` in `~/.claude/settings.json` was a strict **prefix** match, so the dominant Claude Code commit shapes never invoked `pre-commit-check.sh` at all. Re-probed directly and that is false today: a throwaway repo with a deliberately shellcheck-failing staged script was blocked (exit 2, shellcheck output returned as hook feedback) for **both** `cd <path> && git commit ...` **and** `git add <files> && git commit ...`. So the guard has coverage on the shapes that actually matter, and a local commit succeeding *is* evidence the hook ran.
  - **Reproduce in ~30 seconds, and do re-check rather than trusting either entry:** `git init` a temp repo, stage a `.sh` file containing a syntax error, and attempt a commit in the shape you care about. Blocked with shellcheck output = the hook dispatched. Costs nothing and touches no real repo.
  - **One thing this probe cannot distinguish, so do not claim it either way:** whether the `if` clause is matching liberally, or is unrecognized by the current Claude Code build and the hook is simply running on *every* Bash call. Both look identical from outside, because the script's own first action is a regex gate that exits 0 for anything that is not a git commit. The difference is only a spawn-per-tool-call cost, not a coverage gap. If you need to know, instrument the script — do not infer it.
  - **Why the original entry was wrong is the part worth keeping.** It reasoned from the documented matcher semantics to a coverage claim and never probed the coverage. That is the same defect as a guard that reports success without checking — an unverified claim about a control, just pointed the other way, and arguably worse: it told everyone to distrust a guard that works, which is how a working control gets bypassed by habit. See fleet knowledge `01a03a2c-728c-7ee1-b1f7-8328159264a3`.
- **The CI guard no longer diffs anything — obsolete as of 2026-08-24, and the reason it was replaced.** It used to grep added lines of `git diff BASE HEAD`, which meant it never read the tree it inherited: a fix-forward commit cleared a string from the cumulative diff, and anything already on `main` was permanently invisible. That is why the guard stayed green for four months over a default branch carrying every guarded class. **A delta-only guard certifies a dirty tree forever.** The replacement scans `git ls-files` in full; verify locally with `.github/scripts/fleet_string_guard.py` (no arguments, no pattern to reconstruct).

- **A `.gitignore` pattern with a trailing slash matches directories only — a *symlink* of the same name is not ignored.** `adapters/*/.gitignore` said `node_modules/`, so when something replaced those directories with symlinks the links were untracked-but-not-ignored, and the next broad `git add` staged them as mode-120000 blobs (PR #119, 2026-09-04). Two consequences, both quiet: the committed link carried the authoring host's **absolute path** into a public repo, and because the links happened to point at their own path they resolved to `ELOOP`, so the real installed trees were gone while `ls` still showed a `node_modules` entry. Drop the trailing slash to cover both shapes, and treat `git ls-files -s | awk '$1=="120000"'` as a pre-push check — a symlink is the one file type whose *content* is a path.

## Production deploy checks

- **Production compose does not publish port 3000 to the host.** `ops-brain` listens on `0.0.0.0:3000` inside the container and exposes `3000/tcp` to Docker networks for the reverse proxy; host-local `curl http://localhost:3000/health` is not a valid prod smoke test. Use `docker compose -f docker-compose.prod.yml exec -T ops-brain curl -sf http://localhost:3000/ready` for container/database readiness, `curl -sf https://<your-deploy-host>/health` for public reverse-proxy liveness, or an MCP initialize/tools-list request through the reverse proxy. Caught during the first `Codex-Cloud` deploy smoke on 2026-05-12; updated for the split readiness probe in v5.0.0.
- **`/health` and `/ready` are unauthenticated on purpose.** The bearer middleware skips both so Docker and reverse proxies can probe liveness/readiness without the MCP bearer. `/ready` performs only a minimal database check and reveals no details; `/api` and `/mcp` remain bearer-protected.
- **Deployment target `~/docker/ops-brain` reports as a highly dirty and stale Git branch.** This is a false positive and completely normal. The `deploy-ops-brain` skill runs `rsync` from `~/ops-brain/` to `~/docker/ops-brain/` with `--exclude=.git` to rebuild the container. Because the `.git` folder in `~/docker/ops-brain` is never updated by rsync, the local git index remains frozen at a historical commit while the code files are dynamically overwritten with clean production assets. Do not try to run `git` commands, revert, or pull in `~/docker/ops-brain`; use the development repository at `~/ops-brain` as the clean Git source of truth instead.

- **The `## Surface (N tools)` heading in `CLAUDE.md` is parsed, not decorative.** The deploy host's `deploy-ops-brain` skill reads the expected tool count with `sed -n 's/^## Surface (\([0-9]\+\) tools).*/\1/p' CLAUDE.md` and compares it against the live MCP `tools/list` after the container comes up. Rename the heading, change the parenthetical, or let the count drift from the `#[tool(` stubs in `src/tools/mod.rs`, and the deploy smoke fails or, worse, passes against the wrong number. Nothing in this repo or the stealth dotfiles parses it; the consumer lives only in that skill, which is why a 2026-09-03 review pass mistook the constraint for folklore. Verified by grep on both hosts.

## Compose files

- **`docker-compose.prod.yml` is mandatory for any prod-host compose action.** Two compose files live in the repo:

  | File | Purpose | DB target |
  |---|---|---|
  | `docker-compose.yml` | DEV / new-user — bundles its own postgres | `postgres` service inside dev project's own network, fresh dev pgdata |
  | `docker-compose.prod.yml` | PROD — joins `traefik-net` + `shared-db` external nets | `shared-postgres` (the real production DB) |

  On 2026-04-06 (PR #31 escape-hatch deploy), CC-Stealth ran `docker compose up -d --build ops-brain` without `-f`. The dev file declared `container_name: ops-brain` and `container_name: ops-brain-db`, so compose recreated the production container wired to a fresh empty postgres and ran migrations against zero rows. ~44 seconds of blank-DB serving. Recovery: `docker compose -f docker-compose.prod.yml up -d --build ops-brain`. Cleanup with `docker compose down` ALSO took out the recovered prod container (shared service name). Total downtime ~3 minutes.

  **What PR #33 fixed (2026-04-07):** Dev file is now project-namespaced as `ops-brain-dev` (`name:`, container names, network/volume all suffixed). A stray `docker compose up` from the wrong file on the prod host now spins up isolated `-dev` containers and leaves production untouched. Original incident no longer reproducible.

  **But the rule still stands.** Without `-f docker-compose.prod.yml` you don't get the prod stack — you get an isolated empty dev stack on a different network. Not destructive, but still wrong. Sanity-check after any deploy: `docker exec shared-postgres psql -U ops_brain -d ops_brain -c "SELECT count(*) FROM handoffs;"`. Zero → wrong DB.

  Cleaning up dev orphans on prod host: `docker stop ops-brain-dev ops-brain-dev-db; docker rm ...; docker network rm ops-brain-dev_default; docker volume rm ops-brain-dev_pgdata`. Never touches prod.

- **`docker-compose.prod.yml` enumerates env vars explicitly — no `env_file:`.** When wiring a new env var the binary reads at startup, the PR must touch both:

  1. `.env` on the prod host (actual value)
  2. `docker-compose.prod.yml` `services.ops-brain.environment:` (`- NEW_VAR=${NEW_VAR:-}` so compose substitutes from `.env` into the container)

  2026-05-04 rmcp 1.6 deploy (PR #47) hit this: the binary correctly read `OPS_BRAIN_ALLOWED_HOSTS`, `.env` had the value, but the container booted with `loopback default` because compose had no line to substitute. CC-Cloud caught it from startup log (`HTTP allowed_hosts: loopback default (set OPS_BRAIN_ALLOWED_HOSTS for public deploy)`) and shipped PR #48 (`e3eb232`). Fail-open guard did its job — degraded to loopback rather than allow-all.

  `/prereview` should flag a new `std::env::var(...)` call paired with no compose change. Spot-grep `docker-compose.prod.yml` before approving. The `${VAR:-}` form (empty default) is the right pattern — lets `.env` drive the value while keeping compose valid when unset.

  **The both-places rule scopes to vars *the binary* reads — host-side vars belong in neither.** `scripts/operator-notify.sh` runs on the host under cron, not in the container, so its `OPS_NOTIFY_*` config (`OPS_NOTIFY_AGENT`, `OPS_NOTIFY_TOKEN_FILE`, `OPS_NOTIFY_MAIL_CMD`, `OPS_BRAIN_URL`) is set **inline on the crontab line**. Putting them in `.env` or `docker-compose.prod.yml` is not harmless-but-redundant — it looks configured while the cron job still runs without them. The 2026-07-28 #77 deploy got this right; the trap is a future session pattern-matching the rule above and "fixing" the omission. Rule of thumb: the var is the binary's only if `src/` greps for it. The one piece of #77 that *does* follow the both-places rule is the poller's credential, which rides in the existing `OPS_BRAIN_MACHINE_TOKENS` JSON array the server reads.

## MCP Clients

- **PowerShell 7.2 can corrupt inline JSON passed to native executables.** Its legacy native-argument marshalling may strip embedded quotes from values such as MCP server definitions. The Windows Claude launcher therefore passes its server definition to the Node overlay helper as one native argument under PowerShell 7.4/.NET 8 and validates the generated private config through the Windows CI harness. Do not move the definition back into an inline `--mcp-config` argument; that path is both marshalling-sensitive and invisible to Claude's Channel resolver.
- **Windows live launchers require PowerShell 7.4/.NET 8 for hidden redirected helpers.** `Start-Process -WindowStyle Hidden` was ignored with redirected output (`UseShellExecute=false`) on older runtimes, leaving closable blank consoles beside the Codex TUI. Do not replace it with `-NoNewWindow`: that makes the helper share the launcher's console input and can freeze TUI keystrokes. Keep the 7.4 floor, keep helpers hidden in separate consoles, and pass Codex App Server's `--listen` value as bare `ws://IP:PORT` — converting it through `[uri].AbsoluteUri` adds a trailing slash that Codex rejects.
- **Codex only persists a thread rollout once the thread has content — the clean-launch race.** The Windows launcher starts App Server, then the adapter, then the TUI, so the adapter can discover a brand-new empty TUI thread whose `thread/resume` fails with `no rollout found for thread id <id>`. `#resolveThread()` must latch `targetThreadId` **only after** a successful resume, and must clear a *discovered* latch on failure so the next poll re-lists; latching first strands the adapter on a dead id for the life of the process. A **configured** target (`OPS_BRAIN_CODEX_THREAD_ID`) is never cleared — falling back to "the one loaded thread" could retarget another agent's session on a shared host. Diagnostics matter as much as the fix: the old catch discarded the real error and logged a fixed string, so transport loss (`App Server client is stopped`) and a genuinely unresumable thread produced byte-identical logs and cost CC-HSR a full misdiagnosis cycle during a live rollout gate (2026-08-23). Warnings now carry `cause` + `delivery_stage`, and `index.mjs` logs both. Also: `thread/loaded/list` needs the `initialize` + `initialized` handshake first — a bare connection returns `{"code":-32600,"message":"Not initialized"}`.
- **`Session not found` after idle is server-side, not client-side.** rmcp 1.6's `SessionConfig::DEFAULT_KEEP_ALIVE` is 300s — `LocalSessionManager::default()` evicts every MCP session after 5 minutes of inactivity. Existing MCP clients do not reliably auto-reinitialize on the resulting 404; the user must reconnect (`/mcp` in Claude Code). Mitigated by the keep_alive bump in `src/main.rs` that sets `session_config.keep_alive = Some(Duration::from_secs(3600))` on the `LocalSessionManager`. If `Session not found` recurs anyway, check the new keep_alive is in the deployed binary, then look at rmcp release notes for further session-lifecycle changes.

- **MCP session evicted on container recreate — use the psql escape hatch for closeout.** When the deployer (CC-Cloud, Codex-Cloud) does `docker compose up -d --build ops-brain`, their existing MCP client session against the *running* container is wiped — the in-memory session table goes with the old process. Subsequent MCP tool calls 404 with `Session not found`. The CC MCP client does **not** reliably auto-reinitialize within the same turn. Plan the closeout to use the `shared-postgres` psql escape hatch for `complete_handoff` / `update_handoff` writes, not the MCP path.

  Three observations across deploys: v3.1.0 (`019e1e06` — session survived/reconnected cleanly, lucky), rmcp keep_alive bump (`5ab86c21` — needed escape hatch), v3.2.0 (`c254ceb7` — needed escape hatch). 2 of 3 recreates evicted the session; the v3.1.0 happy path is the outlier, not the norm. This is **unrelated** to the v3.2.0 HTTP `keep_alive` 5min → 1h bump — that fixes idle eviction, not eviction on container restart.

  Deploy skill should pre-stage the psql closeout (`docker exec shared-postgres psql -U ops_brain -d ops_brain -c "UPDATE handoffs SET status='completed', commit_hash='<sha>', updated_at=NOW() WHERE id='<uuid>'"`) so the deployer doesn't have to compose it under time pressure. After successful smoke, if `complete_handoff` MCP returns `Session not found`, drop straight to the escape hatch — do not retry MCP. Retry won't auto-reconnect inside the same turn.

  A remote contributor's session (working from a different machine, separate container relationship) does NOT have this problem — only the deployer's session, which is co-located on the deployment host and has a live session-id against the just-killed process. Possible upstream fix: rmcp HTTP client could auto-reinitialize on 404, but that's out of scope for ops-brain itself.

- **Antigravity CLI (agy) Configuration Schema is strict:** When configuring `ops-brain` (or any HTTP MCP) in the Antigravity CLI, note two critical differences from the standard Gemini CLI:
  1. The configuration file is `~/.gemini/config/mcp_config.json` (not `settings.json`).
  2. The schema is strictly case-sensitive: it **must** be `"serverURL": "https://..."`. If you use `"url"` (the old Gemini schema) or `"serverUrl"`, the Antigravity CLI will fail to load the MCP and throw a `serverURL or command must be specified` error on startup.

## Machine-Filed Handoffs

- **Replies to machine-filed handoffs are invisible to the operating agent's `list_replies_to_me`.** A machine-filed handoff's `from_agent` is the *token binding* (e.g. `Stealth-WS`), not the agent that operates that producer. `list_replies_to_me` matches `parent.from_agent` — so when a recipient replies on-thread, the human/agent who actually cares never sees it via reply tracking. Hit on the very first production wake (2026-07-17): the headless smoke reply threaded to `Stealth-WS` and CC-Cloud (who filed the smoke via that token) would have missed it. Until/unless a design change lands: when replying to an `origin=machine` handoff, ALSO send a direct notify to the operating agent, or address the reply `to_agent` = the operator, not the token binding.

## Auth & identity (per-agent tokens)

- **Identity enforcement depends on one `http` type across `axum` and `rmcp`.** Per-agent token identity (`CallerClass`) travels: `bearer_auth` inserts it into the axum request extensions → rmcp injects that request's `http::request::Parts` (extensions included) into the tool-call context → handlers read it via `helpers::bound_agent` doing `ext.get::<axum::http::request::Parts>()`. That downcast is by `TypeId`, so it only fires when both sides resolve the same `http` type. The streamable-HTTP integration test now drives a real agent-token `create_handoff` mismatch through the entire path and fails if the binding disappears; keep that test and require `cargo tree -i http` to show one version after dependency changes.
- **The `Extension<T>` tool extractor ERRORS when `T` is absent; use the `Extensions` bag.** rmcp's `Extension<T>` returns "missing extension" if the type isn't present — which is every stdio call and any dev path without HTTP parts. Handlers that read caller identity take a bare `ext: rmcp::model::Extensions` (always extractable, possibly empty) and treat absence as unbound. Absence is only reachable on stdio / `--dev-no-auth` (trusted-local); on the public HTTP listener `bearer_auth` always inserts a `CallerClass` before the handler runs.

## Handoff threads and IDs

- **Truncated handoff IDs are ambiguous — always thread on the full UUID.** Handoff IDs are UUIDv7, which is *timestamp-prefixed*: two handoffs filed in the same batch share their leading hex. The per-agent token rollover handoffs CC-Cloud filed on 2026-07-21 were four seconds apart and both begin `019f867d` — `019f867d-639c…` (to CC-Stealth) and `019f867d-72d5…` (to CC-CPA). A note that recorded the thread as just `019f867d` was enough to make CC-Stealth file its completion reply onto *CPA's* thread. The failure is quiet in both directions: `complete_handoff` on the wrong ID returned `Handoff is already completed` (CPA had closed theirs), which reads like success, and the real handoff sat `accepted` until a `check_in` surfaced it. When writing handoff refs into notes, commits, or memory, keep the full UUID or at least enough segments to disambiguate — and after replying, confirm the parent's `to_agent` is actually you.
- **Thread completion does not cascade.** An `action` reply is independent open work even if its parent is later completed; completing the parent cannot safely infer that the reply is also done. This left a resolved gate report sitting `accepted` after its parent rollout had closed. When closing threaded work, reconcile every action-class reply explicitly, attach its own evidence or work ref, and run `check_in` once more to catch an orphan. Notify replies need no lifecycle cleanup.

## GitHub PR Workflow

- **Every CC commits as the same GitHub account, so no CC can formally approve another CC's PR.** `gh pr review --approve` fails with `Review Can not approve your own pull request` (hit on PR #112, 2026-09-03). Post the findings-first pass as a PR comment (`gh pr comment`) and say so on the bus; the review-then-merge role split still holds, GitHub just can't record it as an approval. Don't add a required-reviewer branch rule for this repo — it would block every merge.

- **Canceling a duplicate Actions run can make an otherwise green PR red.** Closing and reopening PR #106 to refresh a stale head association started a second check suite for the same commit. GitHub's PR rollup followed the newer check names, so canceling that duplicate left the latest `Security Audit` canceled even though the earlier suite was fully green; the audit had to be rerun before the PR was green again. If a refresh creates duplicate runs, let the newest required checks finish. An older green run is useful evidence, but it does not guarantee the current PR rollup stays green.

- **Editing a PR body does not retract it — GitHub keeps the old revisions, and they stay world-readable.** Measured 2026-08-24 on PR #85. When a fleet-private string reaches a PR description, the reflex is to edit the body and force-push; the fleet has treated that as remediation. It isn't. GitHub retains every prior revision as a `userContentEdits` node with `deletedAt: null`, queryable over GraphQL by anyone with read access — which on a public repo is everyone:

  ```
  gh api graphql -f query='{ repository(owner:"OWNER",name:"REPO") {
    pullRequest(number:N) { userContentEdits(first:20){ totalCount nodes{ editedAt deletedAt diff } } } } }'
  ```

  Same applies to issue and comment bodies. Treat a string that has *ever* been in a PR body as published — the edit changes what's rendered, not what's retrievable. Related: a force-push does not unpublish the pre-push commit either, and the blob is served by the blobs API independently of the commit, so naming only the commit in a cleanup request leaves the blob reachable. Verify reachability with a *paired control* (a fabricated SHA returns 422 for commits / 404 for blobs) — a bare 200 proves as little as a bare 401.

- **`gh pr merge --delete-branch` on a stacked PR's base CLOSES the stacked PR — GitHub does not retarget it.** Hit on the v4.1.0 audit series (2026-07-17): #66 was stacked on #65's branch; merging #65 with `--delete-branch` auto-closed #66, and a closed PR whose base ref is gone can be neither reopened nor retargeted (`gh pr reopen` / `gh pr edit --base` both fail). Recovery is a rebase onto main (`git rebase --onto main <old-base-tip> <branch>`), force-push, and a fresh PR. When merging a stack bottom-up, either skip `--delete-branch` until the whole stack is in, or expect to re-file the upper PRs.

- **After a squash merge, "this commit is not on any remote branch" proves nothing about whether its content shipped.** Squashing rewrites SHAs, so *every* pre-squash commit reports local-only forever — `git branch -r --contains` and `git cherry` both say "unpushed" for work that is already on `main` inside the squash. Nearly cost three commits on 2026-08-26: `gh pr merge --delete-branch` moved the checkout onto a local `main` that was 5 ahead / 3 behind origin (the deleted branch leaves you somewhere, and that somewhere is a `main` nobody has fast-forwarded). Two of the five were the pre-squash form of the previous PR and already shipped; three were genuinely unpushed rulings that `git reset --hard origin/main` would have destroyed silently.

  **Compare content, not SHAs, before resetting a diverged branch.** One command separates the two cases: `git diff --stat <local-branch> <the-squash-commit>` — files that differ are the real divergence, and an empty diff means the local commits shipped under different SHAs. Confirm with a distinctive string per commit (`git show origin/main:FILE | grep -F`). Tag before resetting (`git tag rescue/<branch>-<date>`); it costs nothing and the reflog is not a plan.

  Note the second-order trap: this repo squash-merges, so **local `main` accumulates pre-squash commits and drifts by default**. If you never fast-forward it, every subsequent `git checkout main` lands you on stale code — and when launcher symlinks resolve through the checkout (see *Live messaging*), that silently runs the old client while `git log` on the PR says the fix is merged.

- **An unmergeable PR is an unscanned PR — a conflicted PR shows no failing checks, it shows no checks.** Found by CC-CPA on PR #116 (2026-09-03). GitHub builds `pull_request` events against the `refs/pull/N/merge` commit, so when the branch conflicts with the base that ref does not exist and **no `pull_request` workflow runs at all** — including `Secret scan` / the fleet-private string guard. The PR page reads as "waiting", which is indistinguishable at a glance from "queued", and the reflex is to fix the conflict last. On #116 the guard's first real run — after the rebase — caught a fleet-private host name on `TODO.md:10`, and the same string was also in the commit message and the PR body. **Rebase first, then read the checks**: a green-looking PR that has never been mergeable has been scanned by nothing.

  **Second way to get an unscanned PR, same consequence: a stacked PR.** Both `ci.yml` and `secret-scan.yml` are `pull_request: branches: [main]`, so a PR whose base is another *branch* matches no trigger and runs **zero** checks — not pending, not queued, absent, with `mergeStateStatus: CLEAN` next to them. Measured on PR #119 (2026-09-04), stacked on #118. It self-corrects when the base merges and GitHub retargets the PR to `main`, but until then the stack's upper PRs are unverified by CI. **Never merge a stacked PR on the strength of the base's checks** — wait for the retarget to produce its own green, and run `.github/scripts/fleet_string_guard.py` and the relevant suite by hand meanwhile. The residue rules still apply to whatever the rebase rewrites (see the `userContentEdits` and blob-reachability bullets above) — the original commit object and body revision stay reachable.

  **What the retarget found, so this is not a hypothetical.** #119 was retargeted onto `main` and its first-ever CI run failed immediately, on a test that read the developer's real profile instead of the pinned fixture (see the isolation bullet under *Live messaging*). The defect had been in the branch for its whole life, behind a `CLEAN` merge state and a green base. Merging on #118's checks would have shipped it.

## Live messaging (Channels / adapters)

- **A source-checkout client install follows the checkout, not the commit that was installed.** The Linux installer creates command symlinks into `scripts/`; it does not snapshot those files. A clean status at one revision followed by a branch switch or pull means the next `ops-brain-claude` / `ops-brain-codex` invocation runs different code with unchanged command paths. Use a pinned clean checkout (or an extracted release bundle), verify the intended tree, and perform no Git operation in that checkout until the attended gate tears down.

- **A registered live peer is not a receiving peer, and the bus cannot tell you which one you have.** The adapter opens its own connection to `/live` and registers on startup — independent of the client's MCP handshake and independent of whether the Channel ever bound. So `list_live_peers` can show a peer with the correct `agent_name`, correct `label`, and `send_live_message` can return `host_accepted`, while the session behind it receives nothing. Measured on stealth 2026-08-24 during the paired gate: a healthy-looking `CC-Stealth` peer in front of a session whose Channel had failed to resolve. `host_accepted` means the target adapter took the bytes, not that a session got them. **Prove a lane with a delivered marker read back from the other side; peer presence is a prerequisite, never the check.** This is the same failure shape the Codex runbook already warns about (App Server starts, `readyz` passes, registration still never happens) — everything upstream succeeds, so it looks healthy right up to the point it isn't.

- **`--mcp-config` servers are invisible to the `--dangerously-load-development-channels` resolver.** The resolver enumerates only the `enterprise`, `user`, `project`, and `local` config scopes and asserts the channel's server name exists in one of them; a server passed on the command line is in none, so launch prints `server:<name> · no MCP server configured with that name` even though `/mcp` shows that server **connected**. `--mcp-config` loads it; only the resolver uses the narrower lookup. **Not version drift** — the function is byte-identical in Claude Code 2.1.231 and 2.1.241. A real interactive 2.1.241 control proved the file form fails too, closing the last unmeasured variant. The supported launcher now creates a private per-launch `CLAUDE_CONFIG_DIR` overlay and places the server in that overlay's user scope. The resolver sees it, while ordinary and wake sessions never do; the real config is not mutated and the overlay is deleted on exit. Do not replace the overlay with ambient local/user registration.

- **`CLAUDE_CONFIG_DIR` replaces the user config; it does not layer over it.** Point it at a directory whose `.claude.json` holds a single MCP server and `claude mcp list` returns exactly that one — every real server disappears. Measured on stealth 2026-08-24. The supported launcher therefore puts the internal Channel entry plus only a recognized theme and literal `hasCompletedOnboarding: true` in its private overlay, then passes the real user `.claude.json` with `--mcp-config`. The resolver finds the Channel in user scope while ordinary MCP servers load directly from their original file, so account metadata, MCP definitions, and credentials are never copied. Also note `.claude.json` lives *inside* `CLAUDE_CONFIG_DIR` when that variable is set, and at `~/.claude.json` when it is not.

- **A Windows Claude adapter log may have no disconnect record even after clean teardown.** Claude Code 2.1.257 normally terminates the MCP child outright, so the Node process receives neither the WebSocket `disconnected` event nor `SIGINT`/`SIGTERM`; both measured logs ended at `live adapter connected`. This does not imply a stale peer: the v5.2.1 attended gate measured remote disappearance and zero owned processes after exit. Use the gate's native-exit timestamp, process check, and remote peer polling on Windows. A terminal log record would require a launcher-owned stop mechanism that reaches the adapter before Claude kills it.

- **You cannot probe whether a `claude` flag exists by pairing it with `--version`.** `claude --any-bogus-flag-at-all --version` exits 0 and prints the version — `--version` short-circuits argument validation, so an accepted flag proves nothing. `--dangerously-load-development-channels` is real but absent from `--help`. To settle flag existence, grep the binary (`~/.local/share/claude/versions/<v>`, an ELF around 340 MB) and use a known flag such as `dangerously-skip-permissions` as a positive control.

- **`claude -p` does not evaluate development channels, so it cannot be used to test them.** A deliberately bogus `--dangerously-load-development-channels server:does-not-exist` in `-p` mode produces no warning at all. Any headless "the channel resolved fine" result is void. Test channel binding interactively, and pair it with a bogus-name control so silence is distinguishable from success.

- **A permission-blocked test suite in a wake session is not a failing test suite, and the two are easy to confuse in a handoff.** The headless wake sandbox denies loopback `bind()`, so every socket-backed test in `adapters/codex-app-server` errors out; an agent working that way can only run the focused, in-memory subset and will honestly report the rest as unverified. The same `npm test` run interactively on the workstation is **35/35, 0 skipped**, sockets included (measured 2026-08-26 publishing #103). Before escalating "tests could not run" to another host or holding a fix on it, re-run it in an ordinary interactive session — the constraint is the sandbox, not the machine and not the code.

- **`thread/loaded/list` is process-global, so a loaded-thread *count* is not a target selector.** Codex CLI 0.150.0 exposes a second, in-memory thread with no persisted rollout on a clean TUI launch, which made the adapter's old exactly-one-loaded invariant unsatisfiable rather than merely dirty — it blocked registration forever with everything upstream green. Discovery keys on `thread/resume` succeeding since #103, but currently treats *every* resume RPC rejection as a non-candidate because App Server has no pinned machine-readable no-rollout code. On a shared or multi-thread App Server, an unrelated rejection on one real rollout can therefore make another appear uniquely viable; pin `OPS_BRAIN_CODEX_THREAD_ID` rather than relying on discovery. Two further consequences: `thread/resume failed: no rollout found` during startup is the normal selection mechanism, not a fault; and the decisive warning is written to `~/.local/state/ops-brain-live/codex-adapter.*.log`, which a `script -q -c` receipt of the foreground client does **not** capture.

- **A `[[ -t 1 ]]` probe inside `$(...)` is always false — the first cut of `--auto` ran every terminal launch as ordinary Claude (2026-09-03).** `reason=$(auto_passthrough_reason "$@")` captured the function's stdout, so its `-t 1` was asking about the capture pipe, not the terminal, and `--auto` silently passed through on a real TTY. Only the pty-driven test caught it (the fake `claude` recorded no Channel flag). Fix: call the function for its exit status, never inside a substitution. Rule that generalises: any TTY probe has to run in the launcher's own stdio, and the test that matters is the *live* shape under a pty, not only the passthrough shapes.

## Client bundle / dependency manifest

- **A CHANGELOG version does not prove a release artifact exists.** Versions 5.0.0 and 5.1.0 have changelog sections and crate versions but were never tagged, so artifact history jumps from v4.2.0 to v5.2.0. Check tags or Releases before telling an operator to install a named bundle; backfill those historical tags only if the missing artifacts become useful.

- **A test fixture that isn't shaped like the shipped artifact will pass while the product is broken.** Found 2026-08-24 re-reviewing the v5.1.0 launcher patch. `test-live-launchers` asserts the right invariant — `doctor claude` reports `claude adapter: ready` while the codex adapter is missing — and it passes. But its fixture is a hand-built directory with no `DEPENDENCIES.json`, and `build-client-bundle` runs `write-deps-manifest` unconditionally, so **every** shipped bundle has one. With the manifest present, `dependencyEntries()` walks *both* adapters regardless of the client argument, so perturbing only `adapters/codex-app-server/node_modules` flips `deps-status claude` to `missing-or-invalid` and `doctor claude` to exit 1 blaming the untouched claude adapter. Green suite, broken product. **Build the real bundle and perturb it** when the invariant is per-client scoping — a fixture is only evidence for shapes the fixture actually has.

- **An integrity manifest that is only consulted when present is defeated by deleting it.** Same review. The check was `if (existsSync(manifest) && !verify(manifest)) return 'missing-or-invalid'` — so removing `DEPENDENCIES.json` from a tampered bundle returns `ready`. In a bundle context an absent manifest must be `missing-or-invalid`, not `ready`. Same fail-open family as the empty-ntfy-topic 200 and the empty-needle scan table: the failure state and the healthy state are byte-identical to the operator.

- **`git commit -a` silently omits untracked files that the build already depends on.** `scripts/read-ops-brain-agent-token.ps1` was referenced by `build-client-bundle`, `test-live-launchers`, and `start-ops-brain-live-adapter.ps1` while still showing as `??`. Local tests all passed because the file was on disk. Caught in review before it shipped (the author did use `git add`), but the window is real and silent: every check is green while the artifact is one file short. `git status --short` for `??` entries before committing a patch that adds a required script.

- **`node --test test/` fails with MODULE_NOT_FOUND on Node 26 — the invocation is bare `node --test`** from the adapter directory (that's what `package.json` `"test"` runs). The failure looks like a real test failure, complete with `fail 1`, and has already been misread once as "the suite is broken".

- **The Claude adapter's stderr goes nowhere, so a live channel that never binds looks exactly like one that did.** Measured on stealth 2026-08-26 during the paired gate. Claude Code spawns the adapter as an MCP server and discards its stderr: the mismatch warning appears in no terminal, and Claude Code's own log for the server records only `Successfully connected (transport: stdio)` and `Channel notifications registered` — that is the **stdio MCP transport, not the `/live` WebSocket**, so the only available evidence reads as success. This is what made the Claude half of gate step 7b unmeasurable while the Codex half, whose launcher redirects adapter stderr to a log file, produced a clean result from the same fault. The adapter now writes its own `claude-adapter.*.log` under `OPS_BRAIN_LIVE_STATE_DIR` for exactly this reason; the launcher cannot redirect it, because Claude Code owns the process. **Asymmetric observability between two halves of one lane is a defect in the lane, not a quirk of one client** — the half you cannot see is the half that will fail silently.

- **A bound-identity mismatch used to retry forever, re-sending the bearer on every attempt.** Both adapters compared the server-returned slug on the `registered` frame and closed the socket, which surfaced as a generic `live connection closed before registration` — the specific reason was discarded by the close handler, and the reconnect loop treated a permanent configuration fault as a transient transport one. Observed looping in a real 7b run. Fixed by marking the error non-retryable and stopping the loop. **When a close handler rejects with its own generic error, it overwrites whatever precise cause triggered the close** — preserve the reason before closing, or every specific failure downgrades to "connection closed".

- **A UTF-8 BOM on a `.ps1` fails the Linux job, and the error names the wrong thing.** Both PowerShell launchers picked up a BOM on the authoring host (PR #116, 2026-09-03). `scripts/test-live-launchers` greps `^#requires -Version 7\.4$` against line 1, and the three BOM bytes sit in front of the `#`, so the anchor never matches and the failure reads as a missing or malformed `#requires` line rather than an encoding problem — you go looking at the text, which is correct. PowerShell itself does not care, so it only ever fails in CI, on the *Linux* job, for a Windows file. Editors on Windows add it back silently. Check with `head -c3 <file> | xxd -p` (`efbbbf` is the BOM); write with `[Text.UTF8Encoding]::new($false)` from PowerShell.

- **`sed -i` on a CRLF file under Git Bash rewrites it to LF, and three independent checks will all tell you it didn't.** Hit by CC-CPA on PR #116 (2026-09-04), cost an hour. MSYS tools normalise line endings on read, so after the damage `grep -c $'\r$'` still reports the file as CRLF; `diff` reports two identical files as wholly different; and with `core.autocrlf=true` `git diff --stat` is perfectly clean. Every tool you would reach for to confirm the suspicion agrees with each other and all of them are wrong — only a byte count from outside MSYS (`[IO.File]::ReadAllBytes($p).Length` in PowerShell, or `wc -c` on a copy made outside Git Bash) tells the truth. Same class as the BOM bullet above and better hidden, because a BOM at least fails loudly in CI. Edit CRLF files from PowerShell, or verify by byte count, never by `grep`/`diff`/`git diff`.

- **A test that reads the developer's real profile passes on the host that wrote it and nowhere else.** `scripts/test-live-launchers` routes every launch through the `LIVE_ENV` array, which pins `XDG_CONFIG_HOME` to an unconfigured directory so a configured host cannot answer for the fixture. Two assertions added in PR #119 invoked `ops-brain-claude --dry-run` / `--help` bare, outside it: green on stealth, failing on CI's first run of that PR (2026-09-04). The trap is that the leak makes the test *more* likely to pass, so a local green is the expected result and evidence of nothing — and what it passed against is the developer's real configuration, the one environment the harness exists to exclude. **Prove an isolation-sensitive suite with a paired control before pushing:** run it once as `XDG_CONFIG_HOME=$(mktemp -d) scripts/test-live-launchers`. If that disagrees with your normal run, the suite is reading your box, not the fixture.

- **The same suite needs the adapter dependencies installed, and the failure names something else.** A fresh worktree has no `adapters/*/node_modules` (gitignored), so `scripts/test-live-launchers` stops there. Until #122 the message was `FAIL: expected output to contain: claude adapter deps: ready`, which reads as a launcher regression rather than a missing install, and sent two agents looking at the wrong code in one week (CC-Cloud reviewing #118, CC-Stealth on #119, 2026-09-04). CI installs them first and never sees it; it is local-only. **Since #122 the suite names its own remedy** — the failure now reads `adapter dependencies are not installed. This is not a launcher failure.` followed by the two commands, so that is the string to grep for; the old one is kept here only so a search from an older checkout still lands. Run `npm --prefix adapters/claude-channel ci --ignore-scripts` and the same for `adapters/codex-app-server` before the suite. Extra trap while #119 was in flight: its parent branch carried the accidentally-tracked `node_modules` **symlinks**, so checking that branch out materialised them and the suite passed — the failure surfaced only after the commit that untracked them, looking exactly like the fix had broken something.
