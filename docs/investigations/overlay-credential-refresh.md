# Live overlay loses Claude credential refreshes

Working notes for one open defect (`TODO.md` → "live overlay loses every Claude
credential refresh"). **Delete this file when the fix ships.** Observations are
pinned to the client versions named inline; re-measure before relying on them.

- **The live overlay loses every Claude credential refresh: the client rewrites `.credentials.json` by rename, replacing the overlay's symlink with a real file that the exit trap then deletes. Read from the 2.1.261 binary + overlay probe on stealth, 2026-09-04, falsification and re-read the same day; affects every live launch on Linux and Windows.** The *read* is **not** blocked — the second half of the original headline ("the client refuses to read a symlinked `.credentials.json`") was falsified the same day and is corrected below; do not re-derive it from an older revision of this bullet. The earlier framing in this bullet ("the overlay snapshots `.credentials.json`") was **wrong** and is corrected here; CC-CPA caught it from the shared code (`01a06e52`). What actually happens:
  - `create-claude-channel-overlay.mjs` **symlinks** `.credentials.json` like every other file entry (`mirrorConfigFile` → `symlinkSync(..., 'file')`). Only `.claude.json` is a real file — it is skipped in the mirror loop and rewritten minimal. Verified by building an overlay and reading the entry types, not inferred.
  - ⚠️ **Falsified 2026-09-04 by measurement on kensai-cloud, after this bullet merged — a live session *does* read the durable credential.** The claim here was that the store opens the path `O_RDONLY|O_NOFOLLOW`, that a symlink therefore yields `ELOOP` → a `refused-symlink` state folded into "no credential", and that this is why a `/login` was demanded. It does not reproduce on **2.1.261**, three ways: a config dir whose only credential entry is a **symlink** to the durable file authenticates headlessly (`CLAUDE_CONFIG_DIR=$dir claude -p …`, exit 0, symlink intact, durable file mtime- and byte-identical); the **negative control** — same dir, credential entry removed — fails `Not logged in · Please run /login`, exit 1, so the symlink genuinely was the credential source; and the measuring session was itself overlay-launched with a symlinked `.credentials.json` and `CLAUDE_SECURESTORAGE_CONFIG_DIR` unset, authenticated throughout. The first review of this PR grepped for the `refused-symlink` and `O_NOFOLLOW` strings, called it "re-derived", and merged; the behavioural test came after. **Nothing in the incident needs the read to be blocked** — the stealth session started with an already-expired token, the client refreshed, the refresh landed in the overlay, and the exit trap ate it. The refresh half below is untouched by this correction and is the whole defect.
  - **The `O_NOFOLLOW` store is latent, not irrelevant — and that changes the reason the fix is right (re-read on stealth at 2.1.261, 2026-09-04).** The correction above is sound, but "a string in a 215 MB bundle is not evidence that it sits on the credential-read path" understates what is there: that module's own `storePath` is `join(Hy(), '.credentials.json')`, so it does target this exact file, and it does map `ELOOP` → `refused-symlink`. The reason it is inert is that it is a **second** store — a separate module resolves the same `Hy()` + `.credentials.json` through an ordinary open with no `O_NOFOLLOW` (and carries the plaintext-storage warning), and the consumers reach for the strict one only behind a gate, of the shape `if (O() && store !== undefined) { …readCredentialsStrict/probeCredentials… }`, falling back to a plain `mtime`/read of the same path when it is off. So the accurate statement is **not** "the strings mean nothing" but "**two stores resolve the same path and the strict one is gated off in this build**". The gate being off for Linux 2.1.261 is *inferred* from the behavioural pair above, not read directly — the slice read that would have named `O()` was refused by the auto-mode classifier, and binary credential forensics is not worth pushing past a refusal. **Two consequences.** (1) A build that flips that gate on reproduces the originally-claimed failure exactly, presenting as "no credential → `/login`" — so this is a latent break of the symlink overlay, not a closed question, and it is worth re-running the three-command pair on each client bump. (2) It is a *second, independent* reason `CLAUDE_SECURESTORAGE_CONFIG_DIR` is the right fix rather than a symlink tweak: pinning it takes the overlay off the credential path entirely, immunising against both the present rename-detach and the latent refusal. **The transferable rule** — finding a mechanism in the code proves it *exists*, never that it *runs*; where two implementations resolve one path, only a positive-and-negative behavioural pair says which is live.
  - `writeCredentials` calls the atomic arm (`exactMode` set) — **temp file + rename**. The rename replaces the overlay's symlink with a real file holding the fresh token, which is what was measured. `cleanup_overlay`'s `rm -rf` on `EXIT INT TERM` then destroys it. The durable `~/.claude/.credentials.json` is never opened for write on any path and keeps its expired value.
  **The fix shape this bullet previously proposed — "symlink the durable document instead of snapshotting it" — is already today's state, so it fixes nothing (it is not, per the correction above, actively broken).** The real fix is an env var the client already supports: `Hy()` (the credential storage dir) reads **`CLAUDE_SECURESTORAGE_CONFIG_DIR` first and falls back to `CLAUDE_CONFIG_DIR` only when it is unset**. Setting it in the launcher — empty string resolves to `~/.claude` explicitly — keeps credentials on the durable real file while `CLAUDE_CONFIG_DIR` still points at the overlay, so **the refresh lands on the durable file instead of a rename into tmpfs**. Justify it by the rename-detach, not by a blocked read: the read is not blocked. The overlay helper should then **skip `.credentials.json` in the mirror loop**, the way it already skips `.claude.json`. Bonus: the keychain account label (`Hge()`) hashes the storage dir when it is non-default, so today's overlay also derives a *different* account name on keychain platforms; pinning the var removes that divergence too. Wants a test that a live session authenticates from the durable file and that the file is byte-identical afterwards.
  **Remote Control (unchanged, still inference as to which key).** `.claude.json` genuinely is a real file: skipped in the mirror, rewritten with onboarding preferences plus the single channel server, so every other durable top-level key is absent by construction. MCP servers survive separately via `--mcp-config`; non-MCP keys do not. That asymmetry is a code fact — *which* key drives interactivity is not. Settle it by launching once with `command claude`.
  **Consequence for explicit live sessions:** this remains a launcher issue to measure when the fleet chooses live; ordinary launches now avoid the overlay. **Windows differs in file type, though no longer in outcome:** `mirrorConfigFile` uses `fs.linkSync` there — a **hard link** rather than a symlink. With the read-refusal falsified above, both platforms now read the durable token fine and both lose a refresh to the same rename-detach, so the gates are measuring the *same* failure by two routes. Keep the distinction only for the file type: a fix that special-cases symlinks would leave Windows unfixed. Workstation-side detail in gentoo-config `GOTCHAS.md`.
